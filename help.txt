Nice, thanks for pasting the fragment + activity. That helps a lot.

You’ve already got realtime wired up on the repository side, so for the Android app there are really **two separate problems**:

1. **Ordering** – new orders should show at the **top**
2. **Realtime UI update** – the new order should show **without you doing anything** (no manual pull-to-refresh)

Let’s fix both directly in the fragment and then double-check that the data is actually flowing.

---

## 1️⃣ Make new orders show at the **top**

Right now you just do:

```kotlin
private fun observeOrders() {
    viewModel.newOrders.observe(viewLifecycleOwner) { orders ->
        adapter.submitList(orders)
        ...
    }
}
```

This respects whatever order the list comes in (most likely **oldest first**), so the new one lands at the **bottom**.

Update this method to:

* Sort by `orderNumber` **descending**
* Optionally secondary sort by `createdAt` (if it exists on your UI model)
* Scroll to the top **after** the adapter has applied the diff

```kotlin
private fun observeOrders() {
    viewModel.newOrders.observe(viewLifecycleOwner) { orders ->
        // Debug log so we know it's actually firing
        android.util.Log.d("ChefNewOrdersFragment", "newOrders changed, size=${orders.size}")

        // Sort newest orders first (highest orderNumber on top)
        val sorted = orders
            .sortedWith(
                compareByDescending<com.streatfeast.app.models.Order> {
                    // Put valid numbers first, invalid (0) at the end
                    it.orderNumber.takeIf { num -> num > 0 } ?: Int.MIN_VALUE
                }.thenByDescending {
                    // If you have createdAt on the model, this gives stable ordering
                    it.createdAt
                }
            )

        adapter.submitList(sorted) {
            // This callback runs *after* diff is applied, so now we can safely scroll to top
            if (sorted.isNotEmpty()) {
                binding.rvNewOrders.scrollToPosition(0)
            }
        }

        // Show/hide empty state
        if (sorted.isEmpty()) {
            binding.emptyState.visibility = View.VISIBLE
            binding.rvNewOrders.visibility = View.GONE
        } else {
            binding.emptyState.visibility = View.GONE
            binding.rvNewOrders.visibility = View.VISIBLE
        }
    }
}
```

Key point: using the **`submitList(sorted) { ... }`** overload ensures the scroll happens **after** RecyclerView has applied the diff and knows about the new first item.

## 2️⃣ Make sure new orders appear *without* manual refresh

You already have this:

```kotlin
private fun observeNewOrders() {
    viewModel.newOrderDetected.observe(viewLifecycleOwner) { (orderId, orderNumber) ->
        orderNumber?.let { num ->
            Toast.makeText(
                requireContext(),
                "New order #$num received!",
                Toast.LENGTH_SHORT
            ).show()
        } ?: run {
            Toast.makeText(
                requireContext(),
                "New order received!",
                Toast.LENGTH_SHORT
            ).show()
        }

        // Trigger refresh to ensure order appears on top immediately
        viewModel.refresh()
    }
}
```

This means:

* Realtime → ViewModel sets `newOrderDetected`
* Fragment shows toast
* You call `viewModel.refresh()` (network → Supabase → Room → Flow emit → LiveData → observeOrders)

If **you see the toast** for the new order but **don’t see the row until a manual swipe refresh** then one of these is wrong:

1. `observeOrders()` is not getting called after refresh
2. Or it is being called, but the list **looks the same** to DiffUtil (e.g. same objects / same order), so the UI doesn’t visually update.

The change above (sorting + `submitList(sorted) { ... }`) fixes #2 most of the time, because:

* Sorting by `orderNumber` descending guarantees the new order ends up at index 0
* DiffUtil sees a new item and a re-ordered list and updates the UI
* We then scroll to position 0 so it’s visible

You can also tighten `observeNewOrders()` a little:

```kotlin
private fun observeNewOrders() {
    viewModel.newOrderDetected.observe(viewLifecycleOwner) { (orderId, orderNumber) ->
        android.util.Log.d("ChefNewOrdersFragment", "newOrderDetected: id=$orderId, number=$orderNumber")

        val msg = orderNumber?.let { "New order #$it received!" } ?: "New order received!"
        Toast.makeText(requireContext(), msg, Toast.LENGTH_SHORT).show()

        // Ask ViewModel to sync (this will eventually update Room)
        viewModel.refresh()
    }
}
```

If after these changes:

* You see `newOrderDetected` log
* You see `newOrders changed, size=...` log in logcat
* But UI doesn’t change until swipe refresh → then we know it’s **purely an adapter / RecyclerView issue** (not data flow).

If you **don’t** see the `"newOrders changed"` log when a realtime insert happens, then the bug is **upstream** (ViewModel / Repository / DAO), not in this fragment.

## 3️⃣ Quick sanity checklist (no extra code, just things to confirm)

If it’s *still* not working after the fragment changes, check these things in your code (you don’t need to paste them, just compare mentally):

1. **DAO query**
   For “new orders” it should be something like:

   ```sql
   SELECT ... 
   FROM orders 
   WHERE storeId = :storeId AND status = 'Created'
   ORDER BY createdAt DESC;
   ```

2. **ViewModel**
   `newOrders` should be coming from a **Flow→LiveData** chain, not a one-shot fetch:

   ```kotlin
   val newOrders: LiveData<List<Order>> =
       repository.observeOrders(status = OrderStatus.CREATED).asLiveData()
   ```

3. **Repository realtime handler**
   On Supabase Realtime INSERT, it should either:

   * write the new order into Room directly, **or**
   * call `refresh()` which then writes to Room via `replaceStoreData()`.

   You already have logs like `Realtime INSERT: {...}` and `Calling refresh() after realtime INSERT event`, so this is probably OK.
