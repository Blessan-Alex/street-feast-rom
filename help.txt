## Migration Overview

- **Current state (Firebase/Firestore/FCM)**: `StreetFeastApplication` boots Firebase, enables Firestore persistence, creates a local notification channel, registers a foreground listener (`OrderPushWatcher`) for live order updates, and starts `OrderPollWorker` via WorkManager to poll every 15 min for background changes. Local notifications are rendered through `NotificationHelper`; a basic FCM service (`AppMessagingService`) handles remote pushes but depends on Firebase Cloud Messaging topics/triggers that currently don’t run in the background reliably.
- **Proof-of-concept (Supabase + OneSignal)**: The `test_notifications` sandbox app initializes OneSignal in `ApplicationClass`, sets verbose logging, and requests POST_NOTIFICATION permission on launch. `MainActivity` is still a stock UI; no Supabase client or data sync is wired yet. It confirms we can prompt and receive OneSignal pushes when the SDK is initialized correctly.

## Should We Switch?

- **Pros**: Supabase provides SQL (Postgres) with row-level security, functions, and real-time channels that can replace Firestore’s real-time listeners. OneSignal offers richer, reliable background push delivery and segmentation; the free tiers cover moderate volumes without the FCM topic/trigger complexity we have now.
- **Cons & risks**: Supabase free tier has row and bandwidth limits; we lose Firestore’s offline cache unless we add our own (Room/SQLite). We must rebuild auth (Supabase Auth or external IdP) and port Cloud Functions logic. OneSignal adds another vendor and client SDK; we must handle user/device registration explicitly.

## Migration Roadmap

- **Phase 0 – Architecture**
  - Data model mapping: translate `stores/{storeId}/orders` schema into normalized Postgres tables (`stores`, `orders`, `order_items`, etc.).
  - Event flow: design Supabase `Realtime` subscriptions (channel per store) or use database triggers → Edge Functions → OneSignal REST to push background notifications.
  - Security: define Supabase Row Level Security policies mirroring Firebase rules (roles: admin, chef, waiter).
  - Auth strategy: decide between Supabase Auth (email/password, magic link) or existing identity provider; plan migration for current users.

- **Phase 1 – Supabase Backend Setup**
  - Provision project, configure Postgres schema, seed dev/test data.
  - Implement RLS policies and migrations under version control (SQL migrations).
  - Create stored procedures or triggers for order status transitions that currently live in Firebase Cloud Functions (`createOrderNumber`, auto `InKitchen`, etc.).
  - Build Edge Function to call OneSignal when `orders.status` enters `Prepared`/`Created`/`Canceled`, including payload shaping.

- **Phase 2 – Android App Integration**
  - Add Supabase Kotlin client, configure dependency injection, and replace Firestore repositories with Supabase implementations (REST/RPC or realtime channel).
  - Implement offline caching (Room or local JSON) to replace Firestore persistence; define sync conflict resolution.
  - Replace Firebase listeners: `OrderPushWatcher` becomes Supabase realtime subscription; background polling becomes optional fallback.
  - Replace FCM service with OneSignal handlers: register devices with user roles, map OneSignal push payloads to existing `NotificationHelper`.

- **Phase 3 – Notification Orchestration**
  - Device registration: ensure OneSignal tags reflect store/role; update when user switches roles.
  - Edge Function integration tests: simulate status changes, confirm pushes arrive in background/foreground.
  - Update notification UX (sounds, deep links) to ensure parity with current behavior.

- **Phase 4 – Data Migration & Rollout**
  - Build migration job (one-off script) to export Firestore to JSON → transform → insert into Supabase (respecting IDs, timestamps).
  - Dual-write strategy during cutover: optionally sync Firestore + Supabase until confident.
  - Monitoring/observability: set up Supabase logs, OneSignal delivery analytics, crashlytics adjustments.

- **Phase 5 – Cleanup**
  - Remove Firebase dependencies, WorkManager polling, and FCM-specific code.
  - Update documentation, CI/CD, infrastructure, and environment variables (OneSignal App ID/Key, Supabase URL/anon key).

## Edge Cases & Considerations

- Background reliability: confirm OneSignal background pushes work under Doze/Android 13+. Handle notification permission prompts gracefully.
- Offline: without Firestore caching, ensure Room cache sync handles network loss, deduplicates orders, and reconciles server timestamps.
- Security: RLS must prevent cross-store access; Edge Functions should verify payloads before hitting OneSignal.
- Rate limits: Supabase free tier (500 MB storage, 8 GB egress) and OneSignal free notification quota—monitor usage to avoid throttling.
- Testing: add instrumentation/unit tests for new repositories, integration tests hitting Supabase staging, and end-to-end notification flows.
