## 1️⃣ Issue A – “Add Items” still calls `createOrder` → “Table X is already occupied”

### 🧩 Problem (what you saw)

You clicked **Add Items** on an existing DINE_IN order (table 4), added 1 item in preview, hit “Place order”, and got:

> Table 4 is already occupied. Use Add Items or Alter Order.

…even though you *were already using Add Items*.

### 🔍 Evidence from logs

Relevant snippet:

```text
2025-12-11 15:56:51.358  SupabaseOrderRepository  D  createOrder: type=DineIn, table=4, license=null, items=3
2025-12-11 15:56:51.540  SupabaseOrderRepository  D  checkTableAvailability: table=4, available=false, occupiedTables=[2, 4, 5]
2025-12-11 15:56:51.541  SupabaseOrderRepository  E  createOrder failed (Ask Gemini)
```

Key point: **Add Items flow is still calling `createOrder(...)`**, so it:

* Runs `checkTableAvailability(table=4)`
* Sees table 4 is in `occupiedTables=[2, 4, 5]`
* Throws the “Table 4 is already occupied” error

So the *UI mode* is “Add Items”, but the **repo method** is still the “new base order” path.

### 🎯 Intended behaviour

For **Add Items** on an existing DINE_IN order:

* You should **not** call `createOrder`.
* You should call the *child/add-on path* (`addItemsToOrder` / `orders_upsert`), which:

  * Creates a **child order** with `parent_order_id = base.id`
  * Skips table-occupancy checks
  * Emits `ORDER_ADD_ITEMS` in `order_events`
  * Shows an **“Add-on”** chip in the chef UI

### ✅ Fix – Android wiring

### 🎯 Intended behaviour for Alter

On alter:

1. Backend `alter_order_v2` should:

   * Clone old order into a **new** replacement order row
   * Set `is_edited = true` on the **new** order
   * Link `parent_order_id = old_order.id`
   * Mark old order status as **Canceled/Altered**
   * Emit an `ORDER_ALTERED` event into `order_events` with:

     * `oldOrderId`, `newOrderId`
     * `oldOrderNumber`, `newOrderNumber`
     * `tableNumber` / `licensePlate`
2. Android should:

   * Treat the new order as the live one.
   * Chef UI: show **Edited** pill when `isEdited == true`.

### ✅ Fix – use `alter_order_v2` instead of `updateOrderItem`

**Where to look:**

* `PreviewOrderFragment.kt` – `placeOrder()` logic under `editMode=EDIT`
* `OrdersViewModel.kt` – expose `alterOrder(...)`
* `SupabaseOrderRepository.kt` – implement the RPC call
* Supabase side:

  * `supabase/migrations/0030_add_is_edited_to_orders.sql` (the function body of `alter_order_v2`)
  * `order_events` emission inside `alter_order_v2`
  * `supabase/functions/order-events/index.ts` – branch for `ORDER_ALTERED`

**Android-side wiring (conceptual):**

In `PreviewOrderFragment.placeOrder()`:

**Backend checks:**

Inside `alter_order_v2` (in SQL / PL/pgSQL):

* Ensure you:

  * `INSERT INTO orders (...) VALUES (..., is_edited := true, parent_order_id := old.id, ...) RETURNING ...`
  * `UPDATE orders SET status = 'Canceled' (or 'Altered') WHERE id = old.id;`
  * `INSERT INTO order_events(event_type, order_id, payload) VALUES ('ORDER_ALTERED', new.id, <json payload>);`

Verify by checking:

* No `ORDER_ALTERED` row in `order_events` ⇒ edge function has nothing to consume ⇒ **no push**.

* Because you still mutate the same order row, chef just sees items “magically change” with no banner or new card.

Once the flow is switched to `alter_order_v2`, both problems disappear:

* Notifications: handled by `ORDER_ALTERED` in `order-events/index.ts`.
* UI badge: `isEdited=true` drives the pill.

## 3️⃣ Critical bug – Editing after chef marks items “Done” mutates already-prepared quantity

### 🧩 Problem

> “I toggled the malai chaap as done in chef page, and then tried editing from waiter page, it changed the quantity from 17 to 21, the edit worked and chef page now shows 21 is done. That is a major error.”

You’re absolutely right – this is **really bad** operationally:
Chef thinks they already prepared 21 of something that the kitchen physically cooked 17 of.

### 🔍 Why this is happening (from behaviour + logs)

* Chef marking an item as “Done” likely sets some **per-item done state** on the same `order_items` row (e.g. `is_done=true` or `done_quantity = quantity`).
* Since “alter” is still using `updateOrderItem` on the **same order** (Issue B), the waiter changes:

```text
item quantity 17 → 21
```

But the “done” state is not reset. So now:

* `quantity = 21`
* `done_quantity` (or implicit is_done flag) still refers to “all items done”
* Chef UI renders it as **21/21 done**.

The logs show repeated `updateOrderItem` calls and realtime UPDATE events on the **same order id** – there’s no new order created to separate “old cooked items” from “new additional items”.

### 🎯 Intended semantics

For correct kitchen flow:

* Once items are sent to the kitchen (InKitchen/Prepared), **you should not be mutating that same order row** for “edits”.
* Instead, you either:

  1. Create a **replacement order** (the `alter_order_v2` design), or
  2. Maintain explicit `prepared_quantity` vs `requested_quantity` and show the delta properly (more complex).

Your design already chose option **1** (replacement order), so let’s lean into that.

### ✅ Fix options (what to implement)

#### Option A – Strict replacement (recommended; matches your Phase 2.5 design)

* **Disallow** direct `updateOrderItem` on orders with `status ∈ {InKitchen, Prepared}`.
* Force the UI to always use `alter_order_v2` for any changes once the order is in kitchen.

**Backend guard (Postgres / RPC level):**

In the function / API used by `updateOrderItem`:

```sql
IF (SELECT status FROM orders WHERE id = _order_id) IN ('InKitchen', 'Prepared') THEN
    RAISE EXCEPTION 'Order is already being prepared. Use alter_order_v2 instead.';
END IF;
```

Then in Android, catch that and show:

> “Order is already in kitchen. Use **Alter Order** to change it.”

And the Alter path, as described above, will:

* Create a new order with updated quantities
* Mark the old one as canceled/altered
* Emit `ORDER_ALTERED`
* Give chef a **visible edited ticket** instead of silently changing the old one.

#### Option B – Complex per-item tracking (only if you really want inline mutation)

If for some reason you must keep a single order row and mutate it:

* Add columns like `prepared_quantity` / `completed_quantity` on `order_items`.
* When quantity is increased from 17 → 21:

  * Decide whether the extra 4 count:

    * become **unprepared** (`prepared_quantity` stays 17, `quantity`=21)
      → chef sees “17/21 done”
    * or you keep `prepared_quantity` synced, which is what you have now (wrong in your scenario).
* You’d need to adjust all chef UI logic to display “prepared/total” properly.

Given you *already* built edit-as-replacement semantics, I’d seriously recommend staying with Option A and removing this whole class of bugs.

### 🔬 Fields / files to inspect for this bug

* **Tables:**

  * `orders`: `status`, `id`, `parent_order_id`, `is_edited`
  * `order_items`: check whatever fields represent done/prepared state (e.g. `is_done`, `done_quantity` etc.)
* **Code:**

  * Backend function that handles **chef “Done”** toggle

    * Possibly `update_order_item_status`, or a status update on `order_items`
  * `SupabaseOrderRepository.kt`

    * Look for `updateOrderItem(...)` usages and ensure:

      * It is *not* called for “edit” on InKitchen/Prepared orders
  * Chef Android:

    * `PreparingOrdersAdapter.kt`
    * How it maps item-level DB fields to “done” UI state.
