## Phase 1 — Table label correctness (UI + model contract)

### 1.1 Create a shared mapper: `OrderDisplayMapper`

**Add file:** `ui/OrderDisplayMapper.kt`

Responsibilities:

* Convert an `Order` into:

  * `locationLabel` (Table X / EatAway #### / Parcel)
  * `headerLabel` (Location + order number e.g. “Table 3 · #41”)

Rules:

* DINE_IN: use `order.tableNumber` only if valid: `in 1..tableCount` (use `DEFAULT_TABLE_COUNT = 7` for now)
* EAT_AWAY: use `order.licensePlate` else “----”
* PARCEL: “Parcel”
* If invalid dine-in table number → “Table ?”

Example:

```kotlin
object OrderDisplayMapper {
    const val DEFAULT_TABLE_COUNT = 7

    fun locationLabel(order: Order, tableCount: Int = DEFAULT_TABLE_COUNT): String {
        return when (order.type) {
            OrderType.DINE_IN -> {
                val t = order.tableNumber
                if (t != null && t in 1..tableCount) "Table $t" else "Table ?"
            }
            OrderType.EAT_AWAY -> "EatAway ${order.licensePlate?.takeIf { it.length == 4 } ?: "----"}"
            OrderType.PARCEL -> "Parcel"
        }
    }

    fun headerLabel(order: Order, tableCount: Int = DEFAULT_TABLE_COUNT): String {
        return "${locationLabel(order, tableCount)} · #${order.orderNumber}"
    }
}
```

### 1.2 Update ChefPageFragment to use mapper (remove formatTableNumber usage)

**Modify:** `ChefPageFragment`

* Replace every `formatTableNumber(order.orderNumber)` with:

  * `OrderDisplayMapper.locationLabel(order)`
* Replace header text to:

  * `OrderDisplayMapper.headerLabel(order)`

### 1.3 Ensure Order model includes correct fields everywhere

Verify Chef flow is actually receiving:

* `Order.tableNumber`
* `Order.type`
* `Order.licensePlate` (for EatAway)

If missing in DTO mapping:

* Update parsing/serialization in repository layer to include these fields.

**Acceptance Criteria**

* Chef list shows “Table 1..7” only for dine-in
* EatAway shows “EatAway 1234”
* Parcel shows “Parcel”
* Never prints 40/41 as table labels

## Phase 2 — Veg indicator must not react to prepared toggle (UI separation)

### 2.1 Separate “veg indicator” from “prepared state”

Current bug: you reuse a color bar for veg/non-veg but recolor it for prepared.

**Fix:** keep veg indicator purely based on `item.isVeg` (or `vegFlagSnapshot`).

Prepared state must be shown using:

* the switch itself
* optional alpha change on whole row
* optional checkmark icon (recommended for clarity)

### 2.2 Implement in bindItemToView

**Modify binding logic** inside your item rendering:

* Set veg bar color ONCE:

  * green if veg, red if non-veg
* On switch change:

  * do NOT change veg bar color
  * update row alpha OR show a small prepared check icon

Recommended:

```kotlin
val vegColor = if (item.isVeg) 0xFF2ECC71.toInt() else 0xFFF5515F.toInt()
vegBar.setBackgroundColor(vegColor)

val prepared = itemPreparedStates[item.id] == true
row.alpha = if (prepared) 0.6f else 1f
preparedIcon.visibility = if (prepared) View.VISIBLE else View.GONE

switchView.setOnCheckedChangeListener(null)
switchView.isChecked = prepared
switchView.setOnCheckedChangeListener { _, checked ->
    itemPreparedStates[item.id] = checked
    row.alpha = if (checked) 0.6f else 1f
    preparedIcon.visibility = if (checked) View.VISIBLE else View.GONE
    checkIfAllPrepared()
}
```

**Important:** `setOnCheckedChangeListener(null)` before `isChecked` prevents recycled-view bugs.

**Acceptance Criteria**

* Veg bar never changes color when toggling prepared
* Prepared state is clearly visible, but independent from veg/non-veg

## Phase 3 — Per-item prepared notifications (production approach)

### Reality check (important)

Client-only “send notification to waiter” is **not production-safe**, because:

* Chef app doesn’t have waiter device IDs
* Notification sending must be centralized, audited, and retried server-side

✅ Correct approach: **write an item-prepared event to DB**, and trigger notifications from backend.

---

## Phase 3A — Data model for per-item prepared state

You need a durable place to record item prepared state.

Choose one:

### Option A (best): order_items table has `is_prepared`

* Add column `is_prepared boolean default false`
* Each item toggle updates the DB row

### Option B: a separate table `order_item_events`

* Insert event rows like `{order_id, item_id, status, created_at}`
* Slightly heavier but great for audit/history

**Recommended:** Option A if you just need current state.

---

## Phase 3B — Backend notification trigger

Implement one backend mechanism:

### Option 1: DB trigger + Edge Function

* When `order_items.is_prepared` becomes true:

  * trigger calls edge function with payload (orderId, itemName, orderNumber, storeId)
  * edge function sends OneSignal to waiter devices for that store

### Option 2: RPC function `mark_item_prepared(order_id, item_id)`

RPC does:

* updates DB
* sends notification
* returns updated “all prepared?” state

**Recommended for simplicity:** Option 2 (RPC)

RPC contract:

* Inputs: `order_id uuid`, `item_id uuid`
* Output:

  * `all_prepared boolean`
  * `order_number int`
  * `table_number int`
  * `license_plate text`
  * `order_type text`

## Phase 3C — Android client changes (Chef)

### 3.1 Add API call in OrdersViewModel

**Add:** `markItemPrepared(orderId, itemId)`

* calls Supabase RPC
* returns `allPrepared`

### 3.2 Update toggle handler

On checked = true:

* call `viewModel.markItemPrepared(order.id, item.id)`
* update local UI only after success (or optimistically with rollback)

If RPC returns `allPrepared == true`:

* also call existing `markPrepared(order.id)` (so the “order ready” status + ready-order notification still happens)

**Acceptance Criteria**

* Toggling one item sends waiter notification (server-driven)
* When last item is toggled, order-level “Prepared” flow still occurs
* Toggle state persists after app restart (because it’s stored in DB)

## Phase 4 — UX & reliability hardening (must for production)

### 4.1 Disable toggles while network call in-flight

* Prevent double taps and race conditions
* Show loading (tiny progress on row or disable switch)

### 4.2 Handle failures gracefully

* If RPC fails:

  * revert switch
  * show toast/snackbar “Could not mark prepared. Try again.”

### 4.3 Avoid fragment crash from async callbacks

* Ensure all UI updates happen if fragment is added/started:

  * `if (!isAdded) return`
  * use `viewLifecycleOwner.lifecycleScope`
